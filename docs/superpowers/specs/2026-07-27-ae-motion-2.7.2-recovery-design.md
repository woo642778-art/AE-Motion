# AE Motion 2.7.2 Recovery and Integration Design

## Status

Approved and implemented as the Build 840 recovery candidate on `fix/2.7.2-recovery`.

## Immutable input

The only accepted input is the user-supplied `AE Motion 2.7(2).ipa` with SHA-256:

`f72053a38a64ea2dac48e18d248d1b279755e24e0318724015b4fd9356090a6d`

The package process must reject every other input. The input is not treated as the final desired state because three previously requested and separately verified compatibility changes must be reproduced before adding the new UI framework.

## Verified 2.7 compatibility patch set

Exactly three baseline files receive controlled, hash-pinned modifications before 2.7.2 integration:

1. `AEMotionExtensionsHost.framework/AEMotionExtensionsHost`
   - Reproduces the verified Home root-surface visibility guard.
   - Required output SHA-256: `54df320ffc7f467f1ad8c7b80619bcd223c20d088b443aadeddc0fbf383628bb`.
2. `Frameworks/AlightMotion.dylib`
   - Replaces all 1,724 old Telegram promotion strings with `https://t.me/aemotionios` using an equal-length replacement.
   - Required output SHA-256: `781307fb0356d86d3d66bf534cdd06b5cc2824648f44cf868dc9257e9fe12793`.
3. `Info.plist`
   - Changes the Telegram metadata to `by https://t.me/aemotionios` before 2.7.2 release keys are added.
   - Intermediate verified SHA-256: `ea7fdb5e3780fd40533971e8e815b89ce8d4f3b881f64327f716e3c29c88a329`.

The existing framework stays at its original bundle path and remains the primary owner of the existing Home, effects, tracking, matte, depth, 3D, World Studio, settings and asset-library behavior. It is never replaced by a wrapper.

## Root cause being corrected

The rejected 2.7.1 package replaced `AEMotionExtensionsHost` with a wrapper and moved the actual implementation to an unbundled sibling executable named `AEMotionLegacy`. That sibling was not represented as a framework bundle and could fail recursive signing or runtime loading. When it failed, both the existing extensions and the new UI disappeared.

2.7.2 prohibits this architecture. There is no `AEMotionLegacy`, no runtime `dlopen`, and no replacement executable at the existing framework path.

## Integration architecture

### Existing extension framework

The original `AEMotionExtensionsHost.framework` remains at the original app load path. Only the exact verified visibility-guard patch described above is permitted. Its Info.plist and resources remain unchanged.

### New 2.7.2 UI framework

The source-controlled Home Shell is built as a separate, recursively signable framework:

`Payload/AlightMotion.app/Frameworks/AEMotionUI272.framework/AEMotionUI272`

The framework has its own Info.plist, executable, bundle identifier, minimum iOS version and release metadata. Its constructor installs the Home Shell hooks directly. It does not attempt to load or relocate the existing extension framework.

### Explicit Mach-O loading

The app executable receives exactly one appended `LC_LOAD_DYLIB` command:

`@rpath/AEMotionUI272.framework/AEMotionUI272`

The command is written into verified zero-filled load-command padding before the first `__TEXT,__text` section. Existing commands are not moved or replaced. The original `AEMotionExtensionsHost` load command remains earlier in load order.

The patcher fails closed if the baseline hash, architecture, command layout, padding, existing extension command, or executable-section boundary differs from the verified input. Bytes from the first executable section offset to EOF must remain byte-identical.

## Preservation contract

The first recovery candidate permits exactly four existing-file mutations:

- host app executable header and load-command padding,
- the hash-pinned extension visibility patch,
- the hash-pinned Telegram promotion patch,
- app Info.plist Telegram and release metadata.

It permits exactly three added files:

- `AEMotionV272Build.json`,
- `AEMotionUI272.framework/AEMotionUI272`,
- `AEMotionUI272.framework/Info.plist`.

Every other baseline file must remain byte-identical. Existing Home, Asset Library, 3D Studio, World Studio and TikTok markers must remain present. Signing material is removed from the unsigned output.

## Subsequent phases

The following work cannot bypass the physical-device recovery gate:

1. Remove or restyle the duplicate runtime launch overlay.
2. Add the Google Drive asset catalog, small previews, background cache and immediate timeline insertion workflow.
3. Connect 3D editing to actual persistent scenes, rendering and editable timeline handoff.
4. Profile and tune Home/editor scrolling, memory, CPU, GPU, thermal behavior and animation smoothness.

Each phase increments the build number and produces another candidate. New functionality should live in separately signable source-controlled frameworks unless the complete existing extension source lineage is restored.

## Verification levels

### Automated

- Swift tests and source contracts.
- Xcode generic arm64 framework build.
- Framework install-name and architecture inspection.
- Exact input and controlled-patch hash verification.
- Mach-O command and executable-section comparison.
- File inventory comparison.
- ZIP CRC and signing-material checks.

### Physical device

Required before promotion:

- recursive signing of both framework bundles,
- app launch,
- existing extension presence,
- Home Shell appearance and routing,
- existing 3D and World Studio entry,
- existing Cutout, Depth, Tracking and Matte entry,
- background and foreground recovery,
- repeated root-tab navigation,
- memory, CPU, GPU and thermal observation.

Automated verification is never reported as physical-device qualification.
