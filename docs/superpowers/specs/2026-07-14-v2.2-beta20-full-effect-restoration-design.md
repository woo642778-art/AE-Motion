# AE motion v2.2 Beta 20 — Full Effect Restoration Design

**Status:** Approved design  
**Branch:** `feature/v2.2-beta20-full-effect-restoration`  
**Target artifact:** `AE-Motion-v2.2-beta20-unsigned.ipa`

## 1. Problem Statement

Beta 19 has three release-blocking defects:

1. The Add Effects **Other** category is empty.
2. Opening **Extensions & Scripts** can terminate the app.
3. A cumulative set of 130 effect descriptors is absent because previous releases quarantined 114 descriptors during the original integrity pass and 16 more during Beta 19 qualification.

The three symptoms have different root causes and must not be addressed by simply copying files back into the app bundle.

### Confirmed root causes

- **Empty Other category:** Beta 19 required an exact descriptor-hash device pass before assigning an effect to Other. The device evidence manifest contained no passing records, so the selector intentionally produced zero Other effects.
- **Extensions & Scripts crash:** the packaged Beta 19 binary did not match the reviewed source architecture. A previously built host framework was patched to load a second runtime framework. This created a fragile dyld/signing boundary and retained older menu code that the source branch had removed.
- **Missing effects:** quarantine was used as a release mechanism instead of a development queue. Several descriptors have genuine XML, GLSL, render-pass, resource, parameter-range, or default-rendering defects; others were removed by conservative static policy despite potentially repairable behavior.

## 2. Goals

Beta 20 is a single, non-partial release. It must:

- expose all 700 unique baseline effect IDs;
- leave zero effects in the packaged quarantine;
- preserve every effect ID;
- return every effect to its earliest valid original category;
- restore original Other effects to Other without filling a quota;
- replace the Beta 19 binary-patch architecture with one source-built host framework;
- make Extensions & Scripts fail closed at the individual tool-row level instead of terminating the process;
- keep editing functions out of Extensions & Scripts and in their matching host editing context;
- verify default rendering, alpha handling, aspect ratio, resources, thumbnails, add/remove behavior, project reopen behavior, and short final rendering for every restored effect;
- preserve the main app executable byte-for-byte.

## 3. Non-Goals

Beta 20 will not:

- rename effect IDs;
- move effects into categories for marketing or count targets;
- copy proprietary third-party implementation code from unrelated APK, IPA, plugin, or encrypted project assets;
- write directly to the host application's private timeline or project database;
- claim physical-device correctness without recorded device evidence;
- merge prior open pull requests automatically.

## 4. Source of Truth and Inventory

### 4.1 Baseline effect set

A generated `effect-restoration-baseline.json` will contain exactly 700 unique effect records assembled from the earliest complete pre-quarantine source package. Each record contains:

- effect ID;
- original file name;
- original category string;
- original display name;
- original descriptor SHA-256;
- original shader and script hashes when present;
- declared parameters;
- declared textures, buffers, passes, resources, and thumbnail;
- the quarantine generation and reason, if any.

The build must fail when the final ID set differs from the baseline ID set.

### 4.2 Original category rule

Each restored effect returns to the category recorded in the earliest valid baseline descriptor.

- No effect is reassigned to Other merely to populate the tab.
- An effect appears in Other only when its baseline category is exactly `other` after case normalization.
- If a baseline category is not natively exposed by the current host picker, the category proxy must register that category as a synthetic category rather than silently remapping the effect.
- The final category manifest must prove that every effect's packaged category matches its baseline category.

## 5. Distribution Architecture

### 5.1 Clean base

Packaging starts from the verified v2.1 Beta 17 IPA, not Beta 18 or Beta 19. This avoids inheriting forced category assignments and the patched two-framework loader.

### 5.2 One source-built extension framework

Beta 20 packages one `AEMotionExtensionsHost.framework` built from the reviewed branch source.

The package must not contain:

- `AEMotionBeta19.framework`;
- a binary-patched framework load command;
- duplicate extension installers;
- unresolved non-system dylib dependencies.

The framework must contain the Extensions & Scripts hub, contextual editing bridge, diagnostics, project reliability tools, and category proxy in one build product.

### 5.3 Main executable preservation

The host executable is treated as immutable. Packaging records its pre- and post-package SHA-256 and aborts if they differ.

## 6. Extensions & Scripts Reliability

### 6.1 Independent-utility-only hub

The hub contains only tools that can operate independently of a selected timeline object:

- Preset Studio;
- Resource Hub;
- BPM/Frame Calculator;
- Random Values and Expression utilities;
- Effect Integrity and Restoration Status;
- Project Reliability;
- Host Diagnostics.

Transform, graph, velocity, gesture, cutout, depth, dead-frame, and other editing-context features must not appear as hub rows.

### 6.2 Safe tool registry

At startup, the hub creates an immutable registry snapshot. Each row records:

- tool ID;
- title and icon;
- controller factory closure;
- required framework classes and resources;
- availability result.

The factory must never force-cast, force-unwrap, or dynamically invoke an unavailable controller. An unavailable tool remains visible only when useful for diagnostics and opens a nonfatal explanation screen.

### 6.3 Row-level fault isolation

Selecting one tool is wrapped in a guarded presentation boundary. Failure to construct or present a controller:

- records a diagnostic event;
- restores table interaction;
- shows an alert for that row;
- does not terminate or corrupt the entire hub.

### 6.4 Lifecycle tests

The release gate includes repeated open, close, search, favorite, recent, rotation, background/foreground, and rapid-tap sequences. The hub must survive 100 consecutive entry cycles on each required device class with zero crashes.

## 7. Full Effect Restoration Pipeline

The 130 quarantined effects remain outside the distributable effect directory while being repaired. Quarantine is a development queue only; the final IPA contains no packaged quarantine directory.

### 7.1 Repair classification

Each effect is assigned one or more root-cause classes:

- malformed XML or duplicate parameter ID;
- invalid parameter range, default, or step;
- missing shader output;
- unsafe or unbounded shader loop;
- division by a zero-permitting parameter;
- undeclared texture, buffer, or render-pass target;
- unavailable external resource;
- incorrect texture coordinate or aspect-ratio handling;
- alpha destruction;
- blank default output;
- unintended border bars or crop;
- missing or invalid thumbnail;
- unsupported proprietary dependency.

### 7.2 Repair rules

Repairs preserve effect ID and intended user-facing purpose.

- XML metadata is repaired directly when the implementation is otherwise valid.
- GLSL is rewritten when the existing shader is unsafe or incomplete.
- Missing buffers and pass graphs are recreated with explicit declarations and deterministic pass ordering.
- Missing resources are recreated from clean-room assets or replaced by procedural equivalents.
- Effects that depended on unavailable proprietary code receive a clean-room implementation based on observable controls and intended behavior, not copied implementation code.
- Default parameter values must produce a valid visible frame. An effect intended to add black bars must preserve the source at its neutral/default amount and produce bars only when its control is increased.

### 7.3 Family-based internal execution

Although Beta 20 is one public release, repair work is internally divided into reviewable families:

1. metadata and XML-only repairs;
2. parameter and numerical-safety repairs;
3. single-pass shader repairs;
4. multi-pass and buffer repairs;
5. missing-resource and procedural-replacement repairs;
6. alpha, aspect-ratio, crop, and border repairs;
7. thumbnail and discovery repairs.

A family can be marked complete only when every effect in it passes its automated and device qualification record.

## 8. Effect Qualification

### 8.1 Static qualification

Every descriptor must pass:

- XML parse and schema checks;
- unique effect ID and parameter IDs;
- allowed and baseline-matching category;
- finite parameter ranges and valid defaults;
- dependency and resource closure;
- declared texture, buffer, and pass consistency;
- shader output presence;
- loop and numerical-safety checks;
- exact-case thumbnail resolution and positive dimensions;
- deterministic descriptor and resource hashes.

### 8.2 Render fixtures

Every effect is tested against a fixed fixture set:

- opaque landscape color chart;
- opaque portrait color chart;
- transparent RGBA checkerboard;
- high-contrast edge target;
- moving subject clip;
- gradient and fine-detail clip.

For each effect, the qualification runner records:

- default-frame output;
- one meaningful non-default parameter output;
- alpha statistics;
- top, bottom, left, and right border metrics;
- blank/solid-frame metrics;
- output dimensions and aspect ratio;
- render duration and timeout status;
- crash or exception evidence.

### 8.3 Semantic exceptions

Visual rules distinguish defects from intended behavior.

- A cinematic-bars effect may generate bars only when its bar control is non-neutral.
- A matte or alpha effect may intentionally alter alpha when the parameter purpose declares it.
- A solid-fill effect may intentionally generate a solid frame.

Exceptions are effect-ID-specific, documented, and tested. They cannot be broad name-based suppressions.

### 8.4 Device qualification

Final release evidence requires a signed build on at least:

- one iPhone-class device;
- one iPad-class device.

For every restored effect, UI automation or an equivalent recorded host workflow must:

1. locate the effect in its original category and through search;
2. add it to a supported layer;
3. confirm the preview remains responsive;
4. change one meaningful control and observe a preview update before finger release;
5. remove and re-add the effect;
6. save, close, and reopen the project;
7. render a short clip;
8. record the exact descriptor SHA-256, host version, device class, disposition, metrics, and crash-log reference.

No effect is marked `devicePassed` from static analysis alone.

## 9. Other Category Acceptance

The Add Effects picker must contain an Other category whenever the baseline includes at least one original Other effect.

Acceptance requires:

- the category chip appears;
- opening it does not crash;
- the displayed ID set exactly matches baseline Other IDs;
- every displayed effect also appears in search;
- no non-Other baseline effect appears in the category;
- repeated switching between Other and adjacent categories preserves correct index-path forwarding.

## 10. Failure Handling and Build Policy

The final package does not silently omit failed effects.

- A missing or failing effect aborts the Beta 20 release build.
- The build report lists the unresolved effect and exact failing gate.
- Development builds may retain a repair queue, but the distributable IPA must have 700 active effects and zero quarantined effects.
- Extensions & Scripts tool failures are isolated at runtime and logged without app termination.
- Unsupported host UI contracts fail closed by hiding the contextual button rather than guessing selectors.

```text

- Fixed the Other category and Extensions & Scripts crashes.

```

## 14. Completion Definition

Beta 20 is complete only when:

- all 700 baseline effect IDs are active in the IPA;
- all 130 previously quarantined effects have individual repair and qualification records;
- no packaged quarantine remains;
- all effects are in their original categories;
- Other and Extensions & Scripts pass their acceptance tests;
- the one-framework architecture is source-built and its artifact hash matches the packaged framework;
- all automated gates pass;
- physical iPhone and iPad evidence is recorded without unreported crashes;
- no unsupported claim of visual correctness is made.
